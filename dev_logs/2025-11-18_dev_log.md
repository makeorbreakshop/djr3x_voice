```python
async def _handle_person_detected(self, payload: Dict[str, Any]) -> None:
    """Handle VISION_PERSON_DETECTED event."""
    person_name = payload.get("person_name", "Unknown")
    confidence = payload.get("confidence", 0.0)
    timestamp = payload.get("timestamp", time.time())

    # Store current person and update person_memory
    await self.set("current_person_present", person_name)
    await self.set("last_person_detection_time", timestamp)

    person_memory = self._state.get("person_memory", {})
    if person_name not in person_memory:
        person_memory[person_name] = {}
    person_memory[person_name]["last_seen"] = timestamp
    person_memory[person_name]["confidence"] = confidence
    await self.set("person_memory", person_memory)

async def _handle_person_exited(self, payload: Dict[str, Any]) -> None:
    """Handle VISION_PERSON_EXITED event."""
    await self.set("current_person_present", None)
    await self.set("last_person_exit_time", timestamp)
```

## Session 3: Continuous Face Recognition Integration

### Overview
Integrated continuous face recognition monitoring into VisionService. Restored features that were lost during merge conflict in Session 2. System now performs real-time person detection and emits events when people enter/exit the camera view.

### Changes Made

**Added configuration parameters to `__init__`:**

**Added person tracking state variables:**
- `_current_person`: Currently detected person name
- `_current_person_confidence`: Current detection confidence
- `_person_detection_time`: When person was first detected
- `_no_person_frames`: Counter for person absence (hysteresis)
- `_person_exit_threshold`: Frames before emitting PERSON_EXITED (default: 10 frames = 2 seconds)

**Added monitoring task management:**
- `_monitoring_task`: AsyncIO task for continuous loop
- `_monitoring_running`: Flag to control loop execution

#### 2. Face Encoding Loading
**Method**: `_load_face_encodings()`

Loads trained face encodings from `vision_data/face_encodings.pkl`:
- Checks if `face_recognition` library is available
- Loads pickled dictionary of {name: encoding} mappings
- Logs number of people loaded
- Gracefully handles missing file or errors

**Startup behavior:**
- If no encodings found: Logs warning, monitoring disabled
- If encodings loaded: Monitoring starts automatically

#### 3. Continuous Monitoring Loop
**Method**: `_continuous_monitoring_loop()` (async)

Background task that runs at configured FPS:
1. Opens camera for continuous capture
2. Captures frames in loop
3. Runs face recognition on each frame (in thread to avoid blocking)
4. Calls `_handle_person_detection()` with results
5. Sleeps to maintain target FPS
6. Releases camera on stop

**Error handling:**
- Retries on frame capture failures
- Logs errors without crashing
- Graceful shutdown on cancellation

**Lifecycle:**
- Started in `_start()` if enabled + face_recognition available + encodings loaded
- Stopped in `_stop()` with proper task cancellation

#### 4. Face Recognition
**Method**: `_recognize_face(frame)` (sync, called in thread)

Uses `face_recognition` library to identify people:
1. Converts BGR (OpenCV) → RGB (face_recognition)
2. Detects face locations using HOG model (faster than CNN)
3. Computes face encodings for detected faces
4. Compares against all known face encodings using face distance metric
5. Returns best match if distance < threshold

**Returns**: `(person_name, confidence)` or `(None, 0.0)` if no face

**Performance:**
- Uses HOG model for speed (~5 FPS sustainable)
- Runs in thread via `asyncio.to_thread()` to avoid blocking event loop
- Processes only first detected face (assumes single person)

#### 5. Person Detection State Machine
**Method**: `_handle_person_detection(person_name, confidence)` (async)

Implements state machine with hysteresis to prevent event flickering:

**State transitions:**
- **No person → Person detected**: Emits `VISION_PERSON_DETECTED`
- **Person A → Person B**: Emits `PERSON_EXITED` for A, then `PERSON_DETECTED` for B
- **Person → No person (temporary)**: Waits N frames before emitting exit
- **Person → No person (sustained)**: Emits `VISION_PERSON_EXITED` after threshold

**Events emitted:**
```python
VISION_PERSON_DETECTED: {
    "name": "Brandon",
    "confidence": 0.85,
    "timestamp": 1234567890.0
}

VISION_PERSON_EXITED: {
    "name": "Brandon",
    "duration_seconds": 45.2,
    "timestamp": 1234567935.2
}
```

**Hysteresis logic:**
- Person must be absent for 10 consecutive frames (2 seconds at 5 FPS) before exit event
- Prevents flickering from temporary occlusions or detection failures
- Tracks `_no_person_frames` counter, resets on detection

### Technical Details

### Changes Made

#### Face Encoding Format Compatibility
**File**: `cantina_os/cantina_os/services/vision_service.py`

```python
    'names': ['Brandon', 'Brandon', ...]
}
```

**New format** (expected by VisionService):
```python

}
```

**Implementation:**
- Detects format by checking for 'encodings' and 'names' keys
- Converts legacy format on-the-fly during load
- Handles duplicate names (takes first encoding)
- Logs format conversion for debugging
- Falls back gracefully for unknown formats

**Code changes:**
```python
# Check if it's the legacy format
if isinstance(data, dict) and 'encodings' in data and 'names' in data:
    # Convert to new format: {name: encoding}
    self.known_face_encodings = {}
    for name, encoding in zip(names_list, encodings_list):
        if name not in self.known_face_encodings:
            self.known_face_encodings[name] = encoding
elif isinstance(data, dict):
    # New format - use directly
    self.known_face_encodings = data
```

**What Runs Continuously:**

## Session 7: WS2812B RGB LED Ring Upgrade

### Overview
Upgraded DJ R3X eyes from MAX7219 monochrome LED matrices to WS2812B RGB LED rings (2× 7-LED rings). Created new Arduino sketch with enhanced animations and RGB color support. Updated Python services to support color commands.

### Hardware Changes

**Old System:**
- MAX7219 LED driver chips (2 devices)
- 8×8 monochrome LED matrices (red only)
- 3-pin SPI control (DIN, CLK, CS)
- Grid-based animations

**New System:**
- WS2812B RGB LED rings (2× 7-LED each = 14 total)
- Full RGB color (16.7M colors)
- Single-pin data control (Pin 6)
- Ring-based animations
- Daisy-chained configuration

**Wiring:**
```
Arduino Pin 6 → Ring 1 DIN
Ring 1 DOUT → Ring 2 DIN
Both rings VCC → External 5V power supply
Both rings GND → Common ground with Arduino
```

**Power:**
- 14 LEDs @ 50% brightness: ~420mA (safe from USB)
- 14 LEDs @ 100% brightness: ~840mA (requires external 5V supply)
- Default: 128/255 (50%)

### Arduino Sketch Changes

**File Created:** `cantina_os/arduino/rex_eyes_ws2812b/rex_eyes_ws2812b.ino`

**Library:** FastLED (replaces LedControl)

**Extended Protocol:**

Backward-compatible single-character commands:
- Pattern commands: `I`, `S`, `T`, `L`, `E`, `H`, `D`, `A` (unchanged)
- Legacy brightness: `0`-`9` (maps to 0-255)
- Reset: `R`

New RGB commands:
- Color: `CRRGGBB\n` (hex RGB, e.g., `CFF0000` = red)
- Brightness: `Bnnn\n` (0-255, e.g., `B128` = 50%)

**Enhanced Animations:**

1. **THINKING (T)** - Counter-rotating scanning
   - Left eye: Clockwise rotation
   - Right eye: Counter-clockwise rotation
   - 3-pixel trailing fade (100%, 60%, 30%)
   - **Why**: Asymmetry conveys "processing/computing"

2. **LISTENING (L)** - Symmetrical expanding wave
   - Both eyes expand outward from top simultaneously
   - 4-step brightness gradient (255→200→120→60)
   - Expands/contracts like radar ping
   - **Why**: Symmetry = focused attention

3. **SPEAKING (S)** - Multi-wave radiating pattern
   - Three overlapping waves at different speeds
   - Phase-shifted by 2 LEDs each
   - Additive blending creates brightness peaks
   - **Why**: Dynamic rhythm simulates speech

4. **ENGAGED (E)** - Gentle single-color breathing
   - Smooth sine-wave breathing (60%-100%)
   - Center LED brightens during "inhale" (pupil dilation)
   - Replaced rainbow effect (too playful)
   - **Why**: Calm, alert, professional

**Animation Update Rate:** 80ms per frame

## Session 9: Real-Time Control Architecture Design

### Overview
Discovered fundamental architectural gap between event-driven system (good for decisions) and real-time control needs (smooth LED animations, servo motion, audio sync). Current system can't handle 60fps updates through event bus.

### Analysis: Two Communication Types

**Event Bus (Current - Slow/Async)**
- ✅ Perfect for: User commands, mode changes, LLM responses, music selection
- ❌ Can't handle: 60fps LED updates, smooth servo interpolation, TTS amplitude sync
- **Example**: "Play happy animation" (decision)

**Real-Time Loop (Missing - Fast/Continuous)**
- ✅ Needed for: LED brightness following audio amplitude, servo smoothing, beat-sync animations
- ❌ Can't use event bus: Too slow (event overhead >>16ms frame budget)
- **Example**: "Update LED brightness 60x/sec based on audio" (execution)

### How This Works in ROS & Disney Animatronics

**ROS Pattern (Proven)**:
- Topics (event bus): Goals, commands, decisions → "Move arm to position X"
- Control Loops (100Hz+): Smooth execution → Interpolates position over time
- Both run in parallel: Topics set targets, loops execute smoothly

**Disney Animatronics**:
- Pre-recorded timelines: Audio + servo positions + LED frames synchronized
- Playback system: 60fps loop reads timeline, sends to hardware
- Show control: Event-based (start show, stop show, emergency stop)

### Proposed Architecture: Add RealtimeService Base Class

**New Service Type** (alongside BaseService):
```python
class RealtimeService(BaseService):
    """Service with built-in control loop for real-time updates."""

    def __init__(self, service_name, event_bus, loop_rate_hz=60):
        super().__init__(service_name, event_bus)
        self._loop_rate_hz = loop_rate_hz
        self._loop_task = None

    async def _run_loop(self):
        """Runs at specified Hz (60fps, 100fps, etc.)."""
        while self._running:
            loop_start = time.time()

            await self._control_update()  # Subclass implements

            # Maintain precise loop rate
            elapsed = time.time() - loop_start
            await asyncio.sleep(max(0, 1.0/self._loop_rate_hz - elapsed))

    async def _control_update(self):
        """Override with control logic (called every frame)."""
        raise NotImplementedError
```

**How Services Use Both Systems**:
```python
class LEDControllerService(RealtimeService):
    def __init__(self, event_bus):
        super().__init__("led_controller", event_bus, loop_rate_hz=60)
        self._current_animation = "idle"
        self._amplitude_modulation = 0

    async def _on_start(self):
        # Event handlers set STATE (slow decisions)
        await self.subscribe(EventTopics.SPEECH_STARTED, self._on_speech_started)
        await self.subscribe(EventTopics.TTS_AMPLITUDE, self._on_amplitude)

    async def _on_speech_started(self, payload):
        """Event handler - just changes state."""
        self._current_animation = "speaking"

    async def _on_amplitude(self, payload):
        """Event handler - updates modulation value."""
        self._amplitude_modulation = payload["amplitude"]

    async def _control_update(self):
        """60Hz loop - EXECUTES state smoothly."""
        # Calculate LED frame based on current state
        brightness = self._calculate_brightness(
            self._current_animation,
            self._amplitude_modulation
        )

        # Send to hardware (binary protocol, <1ms)
        await self._arduino.write_binary([0xFF, 0xAA, brightness])
```

### Recommended Service Granularity

**Two RealtimeServices to Start**:

1. **LEDControllerService** (60Hz)
   - Controls: Eyes (14 LEDs), Mouth (future), Body lights (future)
   - Why unified: Easier to sync all LEDs (e.g., system-wide pulse)
   - Zones: Separate animation state per LED group

2. **MotionControllerService** (100Hz)
   - Controls: Head pan/tilt servos, future arm/body servos
   - Why unified: Shared motion planning (e.g., head tracks person while arms gesture)
   - Per-servo: Position targets, velocity limits, interpolation

**NOT Recommended**: Per-component services (EyeService, MouthService, HeadService)
- Harder to coordinate (system-wide animations)
- More overhead (multiple control loops)
- Complex cross-service sync

### Integration with Existing Architecture

**Event Bus Role** (unchanged):
- High-level decisions: "Play happy animation", "Look at person"
- State changes: Mode transitions, sentiment detected
- Coordination: Multi-service workflows (DJ mode, conversations)

**Real-Time Loop Role** (new):
- Smooth execution: Interpolate servo motion, run LED animations
- Live data: TTS amplitude → brightness, music beat → pulse
- Hardware I/O: Direct binary communication (fast path)

**They Work Together**:
```
User: "R3X is happy!"
  ↓ Event: SENTIMENT_DETECTED
ClaudeService decides: Play happy animation
  ↓ Event: LED_ANIMATION (zone='all', animation='sparkle', color=green)
LEDController receives event: Sets _current_animation = 'sparkle'
  ↓ Control loop (60Hz): Executes sparkle animation smoothly
  ↓ Hardware: LEDs update 60 times/sec with smooth sparkle effect
```

### Arduino Refactor Needs

**Current Issues**:
- Race conditions: Color + pattern sent as separate commands
- No command queue: Serial buffer only 64 bytes
- Immediate execution: Can't defer or prioritize commands

**Solutions** (if needed later):
- Command queue: 8-command circular buffer
- Atomic updates: Single command contains color+pattern+brightness
- Priority layers: Override, foreground, ambient (like audio timeline)

**For Now** (simpler approach):
- Keep current protocol for pattern changes (event-driven)
- Add binary protocol for high-frequency updates (real-time)
- Binary format: `0xFF 0xAA <brightness>` (5 bytes, <1ms parse)

### Key Insight

**This is the missing layer in CantinaOS**. The event bus is perfect for what it does - but we need real-time control loops for smooth hardware execution. This is how ROS works, how Disney does it, and how all real robotics systems coordinate. We're not replacing the event architecture - we're adding the execution layer underneath it.

**Architecture Evolution**:
- Started: Event-only (good for decisions)
- Adding: Event + Real-Time (good for execution)
- Future: Distributed Real-Time (multiple machines)
