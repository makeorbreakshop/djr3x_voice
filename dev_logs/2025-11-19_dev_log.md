### Overview
Implemented a new RealtimeService base class and refactored EyeLightControllerService to use a 60Hz control loop for hardware updates. This separates high-level decision making (event handlers) from low-frequency hardware execution (control loop).

## Changes Made

### 1. Created RealtimeService Base Class
**File**: `cantina_os/cantina_os/base_service.py`

**New class added after BaseService:**
- Extends BaseService with built-in control loop running at configurable Hz (default 60Hz)
- Designed for hardware control requiring smooth high-frequency execution
- Performance tracking: loop overruns, max execution time, iteration count

**Key features:**
- `loop_rate_hz`: Configurable frequency (60Hz, 100Hz, etc.)
- `_run_control_loop()`: Background task maintaining precise timing
- `_control_update()`: Abstract method subclasses override (called every frame)
- Automatic lifecycle management (starts with service, stops gracefully)

**Architecture pattern:**
```python
class MyHardwareService(RealtimeService):
    async def _handle_event(self, payload):
        # Event handler - just sets state
        self._target_position = payload["position"]

    async def _control_update(self):
        # Called 60x/sec - executes smooth movement
        await self._send_to_hardware(self._target_position)
```

**Performance monitoring:**
- Detects loop overruns (when execution exceeds frame budget)
- Logs warnings every 100th overrun to avoid spam
- Reports total overruns and max execution time on shutdown

### 3. Implemented _control_update() Method

**Core 60Hz control loop:**
```python
async def _control_update(self) -> None:
    # Skip if not connected to hardware
    if self.mock_mode or not self.connected or not self.adapter:
        return

    # Check if pattern changed
    if self._target_pattern != self._current_pattern:
        await self._send_pattern_to_arduino(self._target_pattern)
        self._current_pattern = self._target_pattern

    # Check if color changed
    if self._target_color != self._current_color:
        await self._send_color_to_arduino(self._target_color)
        self._current_color = self._target_color

    # Check if brightness changed
    if final_brightness != self._current_brightness:
        await self._send_brightness_to_arduino(final_brightness)
        self._current_brightness = final_brightness
```

**Helper methods added:**
- `_send_pattern_to_arduino(pattern)`: Sends pattern command via adapter
- `_send_color_to_arduino(color)`: Sends color command via adapter
- `_send_brightness_to_arduino(brightness)`: Sends brightness command via adapter

## BUG FIX: Arduino Serial Buffer Issue

### Problem Identified
Control loop was executing and sending commands correctly, but Arduino was only receiving partial data:
- Python sent: `CFFC832` (7 chars)
- Arduino received: `C832` (4 chars)
- Debug output showed: `DBG:ERROR:Invalid command`

### Root Cause
Arduino sketch violated serial communication best practices:
- Used `if (Serial.available() > 0)` instead of `while` loop
- Read only **1 character per loop iteration**
- Called `return` immediately after reading, exiting loop early
- With `delay(20)`, only checked serial every 20ms
- At 115200 baud, characters arrive every ~0.08ms - **250x faster than checking rate**
- Result: Buffer overflow and data loss

### Solution (Arduino Best Practices)
**File**: `cantina_os/arduino/rex_eyes_ws2812b/rex_eyes_ws2812b.ino`

Changed serial reading pattern to drain entire buffer:
```arduino
// OLD (WRONG)
if (Serial.available() > 0) {
    char inChar = Serial.read();  // Read 1 char
    // ...
    return;  // Exit immediately
}

// NEW (CORRECT - Best Practice)
while (Serial.available() > 0) {
    char inChar = Serial.read();  // Read ALL chars
    // ...
    continue;  // Keep reading
}
```

**Changes:**
1. `if` → `while`: Drains entire serial buffer each loop iteration
2. `return` → `continue`: Keeps reading all available characters
3. Added `&& !readingCommand` guards to prevent command collision
4. Added buffer length check before processing
