## Session 2: Vision Service Optimization - Smart Scene Capture Logic

### Overview
Dramatically reduced Claude Vision API costs by implementing intelligent per-person scene capture cooldowns while maintaining automatic contextual awareness.

---

## Problem Identified

### Excessive Claude Vision API Calls
**Issue**: Face detection flickering caused expensive API calls on every detection change
- Person detected → Scene capture API call ($$$)
- Person briefly lost (head turn, lighting) → Scene capture API call ($$$)
- Person re-detected → Scene capture API call ($$$)
- Pattern repeating every few seconds = massive API costs

**Root Cause**: Scene capture triggered on EVERY person state change, regardless of significance

---

## Solution Implemented

### 1. Per-Person Cooldown Tracking (`vision_service.py`)
```python
# Track when each person was last captured
self._person_last_scene_capture: Dict[str, float] = {}
self._person_scene_cooldown = 60.0  # 60-second cooldown per person
```

### 2. Smart Detection Logic
- **Same person re-detected < 60s**: Skip scene capture (cooldown active)
- **Different person detected**: Always capture immediately (new context)
- **Person exits < 30s duration**: Skip exit capture (likely a flicker)
- **Person exits > 30s duration**: Capture exit scene (meaningful visit)

### 3. Key Code Changes

#### Person Detection Handler:
```python
# Check if we recently captured this person
last_capture = self._person_last_scene_capture.get(person_name, 0)
time_since_capture = current_time - last_capture

if time_since_capture > self._person_scene_cooldown:
    should_capture_scene = True  # Capture allowed
else:
    self.logger.info(f"Skipping scene capture (cooldown: {time_since_capture:.1f}s)")
```

#### Exit Duration Check:
```python
# Only capture exit scene if person was present > 30 seconds
if duration > 30.0:
    should_capture_scene = True
    capture_reason = f"person_exited_{self._current_person}_after_{duration:.0f}s"
```

## Session 3: Serial Buffer Overflow Root Cause & Fix

### Problem Identified
- LED animation timeouts, lost commands, blue flashing on mode changes
- 836 Arduino commands in 3min = excessive
- Pattern transitions timing out

### Root Cause Discovery
- **CRITICAL**: User has Arduino MEGA 2560 (8KB SRAM), not Uno
- Still using default 64-byte serial buffer despite MEGA capabilities
- Buffer fills in ~5.5ms at 115200 baud
- Python waiting for responses while sending = overflow

### Solutions Implemented

1. **Buffer Size Increase**
   - Added `#define SERIAL_RX_BUFFER_SIZE 256` to Arduino
   - 64 → 256 bytes (4x larger)

2. **Fire-and-Forget for Mouth Commands**
   - Modified `set_mouth_amplitude()` - no response wait
   - Prevents blocking during 10Hz updates

3. **Throttling & Deduplication**
   - Mouth updates: 20Hz → 10Hz
   - Only send on value change
   - Buffer flush for critical patterns

4. **Logging Reduction**
   - Mouth commands → DEBUG level
   - Less serial overhead

### Key Learnings
- MEGA 2560 can handle 256-byte buffers easily
- Fire-and-forget essential for streaming data
- Serial vs PWM pins are completely separate systems

**Session Duration**: ~4 hours
**Focus**: Serial buffer optimization, MEGA discovery, fire-and-forget implementation

## V3 Architecture Design

### Layered Animation System
Think of it like Photoshop layers:
1. **Base State Layer**: Core patterns (IDLE, ENGAGED, etc.)
2. **Effect Layer**: Overlays (breathing, blinking, pulsing)
3. **Response Layer**: Real-time inputs (mouth amplitude, flash)

### Key Principles
- **Arduino owns all colors** - No Python color commands
- **State machine pattern** - Clean transitions
- **Single update point** - One FastLED.show() per loop
- **Separated concerns** - State vs animation logic

---

## Implementation Details

### 1. New Command Protocol
```
SI - Set IDLE state (Arduino knows: orange eyes, dark blue mouth)
SE - Set ENGAGED state (Arduino knows: cyan eyes, black mouth)
SL - Set LISTENING state (pulse current color)
ST - Set THINKING state (rotating cyan dots)
SS - Set SPEAKING state (pulse + mouth active)
SF - Trigger FLASH (green confirmation)
Mnnn - Mouth amplitude 0-255 (fire-and-forget)
R - Reset system
```

**SPEAKING**:

## Session 9: Mouth Amplitude Sensitivity & API Connection Optimization

### Overview
Improved mouth LED responsiveness to amplitude changes and eliminated mouse click delays by optimizing API connection warmup strategy.

---

## Mouth Amplitude Improvements

### Problem
Mouth LEDs not sensitive enough to amplitude changes during speech - stayed visually similar even when volume varied significantly.

### Root Cause
Fourth-root compression (`sqrt(sqrt(x))` = x^0.25) was too aggressive, flattening the dynamic range at normal speaking volumes.

### Solution
**Changed from fourth-root to square-root compression:**
```cpp
// Before (Arduino line 634):
float scaledAmp = sqrt(sqrt(normalizedAmp));  // x^0.25 - very aggressive

// After:
float scaledAmp = sqrt(normalizedAmp);  // x^0.5 - balanced dynamics
```

### Impact

| Amplitude | Old Scaling | New Scaling | Improvement |
|-----------|-------------|-------------|-------------|
| 25%       | 70.7%       | 50%         | More contrast at low volumes |
| 50%       | 84.1%       | 70.7%       | Noticeable growth |
| 75%       | 92.4%       | 86.6%       | Still dynamic |
| 100%      | 100%        | 100%        | Full range utilized |

**Result:** Much better visual responsiveness to volume changes during continuous speech.

### Frame Rate Bottleneck Discovery

**Problem:** Even with better amplitude scaling, mouth still looked "laggy" during rapid speech.

**Root Cause:** Python was throttling mouth updates to **10 Hz** (100ms intervals):
```python
self.MOUTH_UPDATE_INTERVAL = 0.10  # 10Hz - TOO SLOW!
```

During rapid speech, multiple syllables can occur in 100ms, making the mouth appear to lag behind the audio.

**Solution:** Increased update rate to **30 Hz** (33ms intervals):
```python
self.MOUTH_UPDATE_INTERVAL = 0.033  # 30Hz - responsive for rapid speech
```

**Why 30 Hz is safe:**
- Arduino runs at 60 FPS (can handle it)
- Serial buffer is 256 bytes (plenty of headroom)
- Fire-and-forget protocol (no response blocking)
- Still has deduplication (only sends if value changed)

**Impact:**
- **Before:** 10 updates/second → sluggish mouth
- **After:** 30 updates/second → 3x more responsive to rapid speech
- Matches typical syllable rates in natural speech (~3-7 syllables/second)

## API Connection Warmup Optimization

### Problem Identified
Every mouse click had a **2-3 second delay** before recording started due to API connection warmup happening on every `MIC_RECORDING_START` event:

```
12:10:09 - Recording start
12:10:09 - Mic recording started - refreshing Claude API connection    ← DELAY
12:10:09 - 🔄 Warming up Claude API connection...
12:10:11 - ✅ Claude warmed up (1.7s)
12:10:11 - 🔄 Warming up ElevenLabs API connection...
12:10:11 - ✅ ElevenLabs warmed up (0.2s)
Total: ~2 seconds of delay per click
```

### Root Cause
**Redundant warmup strategy:**
- ✅ **ENGAGE command** → Warmed up APIs (good!)
- ❌ **Every mouse click** → ALSO warmed up APIs again (redundant!)

The per-click warmup was added as a "safety net" but caused unnecessary delays since HTTP keep-alive keeps connections alive for ~60 seconds.

### Solution
**Removed per-click warmup handlers** from both services:
- `ClaudeService`: Removed `MIC_RECORDING_START` subscription and `_handle_mic_start_for_warmup()` handler
- `ElevenLabsService`: Removed `MIC_RECORDING_START` subscription and `_handle_mic_start_for_warmup()` handler

**New behavior:**
1. **IDLE → INTERACTIVE (ENGAGE)**: Warmup both APIs once (in background)
2. **During INTERACTIVE session**: Connections stay hot via HTTP keep-alive
3. **Each mouse click**: Instant - no warmup needed
4. **INTERACTIVE → IDLE**: Connections expire naturally

## Session 12: Mouth LED Dynamics - AGC for Speech Sensitivity

### Overview
Implemented Automatic Gain Control (AGC) for mouth LED amplitude to show better dynamics during speech. The previous static dB range mapping didn't adapt to the narrow dynamic range of normalized speech audio (-24 LUFS standard).

---

## Problem Identified

### Poor Mouth LED Dynamics During Speech
**Issue**: Mouth LEDs showed minimal variation during normal conversation because:
- ElevenLabs audio is normalized to ~-24 LUFS (broadcast standard)
- Normal speech varies in a narrow range (maybe -30dB to -18dB peaks)
- Static mapping from -60dB to -10dB didn't capture this subtle variation
- Most speech fell in the middle 20-30% of the range

**User Observation**: "The audio doesn't change a lot in terms of loudness, how could we address this?"

---

## Solution Implemented

### Automatic Gain Control (AGC) for Dynamic Range Adaptation

**Core Concept**: Instead of mapping to a fixed dB range, **adapt the range dynamically** based on recent audio content.

**Implementation** (lines 483-530):

1. **Track Recent Audio** (rolling window):
   - Window size: 30 chunks (~0.5 seconds of history)
   - Stores recent RMS values in dB

2. **Calculate Dynamic Range**:
   ```python
   recent_min_db = min(recent_rms_values)
   recent_max_db = max(recent_rms_values)
   dynamic_range_db = max(12, recent_max_db - recent_min_db)
   ```
   - Minimum 12dB range ensures visibility
   - Range adapts to actual speech content

3. **Relative Mapping**:
   ```python
   normalized_amplitude = (db_value - recent_min_db) / dynamic_range_db
   ```
   - Maps current loudness **relative to recent range**
   - Quiet speech → uses full 0-100% LED range
   - Loud speech → uses full 0-100% LED range
   - Always responsive to variations

4. **Moderate Boost**:
   - 2x multiplier (reduced from 4x)
   - Prevents constant saturation
   - Allows peaks to hit full brightness

---

## How AGC Improves Mouth Dynamics

### Before (Static Range):
```
Speech at -28dB → maps to 44% brightness
Speech at -22dB → maps to 56% brightness
Variation: Only 12% LED brightness change
```

### After (AGC):
```
Recent range detected: -28dB to -22dB (6dB range, expanded to 12dB min)
Speech at -28dB → maps to 0% (quietest recent sound)
Speech at -22dB → maps to 50% → 100% after 2x boost
Variation: Full 0-100% LED brightness range!
```

---

## Key Parameters

**AGC Settings**:
- `agc_window_size = 30` chunks (~0.5s)
  - Short enough to adapt quickly to speech patterns
  - Long enough to avoid jumpy behavior on single syllables

- `min_dynamic_range_db = 12`
  - Prevents over-amplification of near-silence
  - Ensures minimum contrast for visibility

- `boost = 2.0x`
  - Moderate boost to utilize full LED range
  - Reduced from 4x to prevent constant saturation

---

## Benefits

### Advantages:
- ✅ **Adapts to actual speech content** - no fixed dB assumptions
- ✅ **Shows subtle variations** - syllable emphasis, word stress visible
- ✅ **Handles quiet and loud speech equally well** - always uses full range
- ✅ **Fast adaptation** - 0.5s window responds quickly to speech changes
- ✅ **Prevents saturation** - 2x boost is moderate, allows headroom

### Technical Benefits:
- Works with any TTS normalization level (-20 LUFS, -24 LUFS, etc.)
- Handles background noise gracefully (AGC finds signal above noise floor)
- No manual calibration needed
- Computationally cheap (just min/max of 30 values)

## Session 2 Addendum 2: Camera Command Event Subscription Fix

**Time**: Evening Session (continued)
**Duration**: 30 minutes
**Issue**: Camera commands not executing despite correct routing

### Root Cause Analysis

Following **CANTINA_OS_TROUBLESHOOTING.md Section 1.3: Event Topic Subscription Mismatches**, identified classic decorator registration issue:

1. **Symptoms Observed**:
   - Commands routing correctly: `Routing command 'camera list' to service 'vision' on topic 'EventTopics.VISION_COMMAND'` ✅
   - Handlers decorated with `@compound_command` ✅
   - But handlers never called ❌

2. **Problem Identified**:
   - `@compound_command` decorators register commands with CommandDispatcher
   - **BUT decorators don't subscribe handlers to event bus!**
   - VisionService missing explicit subscription to `VISION_COMMAND` topic

3. **Pattern from Working Code**:
   MusicControllerService has BOTH:
   - Explicit subscription: `await self.subscribe(EventTopics.MUSIC_COMMAND, self._handle_music_command)`
   - Decorator handlers with router method

### Solution Implemented

**1. Added Event Bus Subscription** (vision_service.py:271-272):
```python
# Subscribe to vision commands (camera list/select/status)
await self.subscribe(EventTopics.VISION_COMMAND, self._handle_vision_command)
self.logger.info("Subscribed to VISION_COMMAND events")
```

**2. Added Router Handler** (vision_service.py:809-830):
```python
async def _handle_vision_command(self, payload: dict):
    """Route vision commands to appropriate handlers."""
    command = payload.get("command", "")
    subcommand = payload.get("subcommand", "")

    # Build full command name
    full_command = f"{command} {subcommand}".strip() if subcommand else command

    # Route to appropriate handler
    if full_command == "camera list":
        await self.handle_camera_list(payload)
    elif full_command == "camera status":
        await self.handle_camera_status(payload)
    elif full_command == "camera select":
        await self.handle_camera_select(payload)
    else:
        self.logger.warning(f"Unknown vision command: {full_command}")
```

**3. Updated Decorator Event Topics** (vision_service.py:805-819):
```python
@compound_command("camera list", event_topic=EventTopics.VISION_COMMAND)
@compound_command("camera status", event_topic=EventTopics.VISION_COMMAND)
@compound_command("camera select", event_topic=EventTopics.VISION_COMMAND)
```

**4. Added to Help Menu** (command_dispatcher_service.py:420, 457-464):
```python
"Camera Commands": ["camera list", "camera status", "camera select"],

# With descriptions:
"    • camera list           - List all available cameras",
"    • camera status         - Show currently selected camera",
"    • camera select <index> - Select camera by index (from camera list)"
```

### Architecture Pattern

This follows the **standard compound command pattern** used by MusicController:

```
CLI Command → CommandDispatcher → VISION_COMMAND event
                                        ↓
                                  VisionService._handle_vision_command()
                                        ↓
                                  Routes to decorated handler
                                        ↓
                                  handle_camera_list/status/select()
```

### Key Learnings

**From Troubleshooting Guide**:
- Decorators alone are NOT sufficient for event handling
- Must have explicit `subscribe()` call + router handler
- This is NOT documented clearly in decorator implementation
- Same pattern as music commands (which work correctly)
