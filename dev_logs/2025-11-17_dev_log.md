## Technical Details

### Camera Scanning Implementation
```python
@staticmethod
def list_available_cameras(max_cameras: int = 10) -> List[Tuple[int, str]]:
    """Scan for available cameras, validate by reading frames"""
    for camera_id in range(max_cameras):
        cap = cv2.VideoCapture(camera_id)
        if cap.isOpened():
            ret, _ = cap.read()  # Verify it actually works
            if ret:
                # Get specs
                width = int(cap.get(cv2.CAP_PROP_FRAME_WIDTH))
                height = int(cap.get(cv2.CAP_PROP_FRAME_HEIGHT))
                fps = int(cap.get(cv2.CAP_PROP_FPS))
```

## Session 3: YOLO Object Detection Performance Optimization

### 10. Upgraded to YOLO11n Model
- **Switched from YOLOv8n → YOLO11n** (Sept 2024 release)
- 22% fewer parameters than v8
- Higher accuracy on COCO dataset
- Updated model file: `yolo11n.pt` (test_vision.py:789)

### 11. Enabled M1 GPU Acceleration
- **Problem**: Object detection running at 3 FPS (CPU-only)
- **Solution**: Added MPS (Metal Performance Shaders) support
- Changes:
  - `model.to('mps')` at model load (test_vision.py:790)
  - `device='mps'` in inference call (test_vision.py:840)
- **Expected improvement**: 3 FPS → 30-60 FPS (10-20x speedup)

### 12. Optimized Inference Parameters
- Half-precision (FP16): `half=True` for M1 GPU
- Streaming mode: `stream=True` for memory efficiency
- Explicit thresholds: `conf=0.5`, `iou=0.7`, `imgsz=640`
- Process every 2nd frame for balance between speed and responsiveness

### 13. YOLO12 Research Decision
- **Evaluated YOLO12** (Feb 2025 release) but decided against it
- YOLO12 issues: training instability, higher memory, slower CPU throughput
- Ultralytics recommends YOLO11 for production use
- YOLO11n is optimal for DJ R3X's real-time edge device needs

### 14. Resolution Strategy
- **Kept 1920x1080 camera resolution** (not downscaled)
- Rationale: Face recognition downscales to 0.25x (480x270), needs high input res
- YOLO internally resizes to 640x640 regardless of input
- Trade-off: ~10ms extra frame read time for better face recognition quality

- **Inference Speed**: ~15ms per frame (target 30-60 FPS)

## Session 8: Vision Pipeline Performance Deep Dive & GPU Acceleration

### 33. Identified Real Performance Bottlenecks
- **Initial Issue**: Combined pipeline running at 10-12 FPS, expected 15-20 FPS
- **Investigation**: Despite low CPU usage, performance was limited
- **Root Causes Found**:
  - Camera frame read: 32.7ms average (highly variable 2-70ms)
  - Display rendering: 20-97ms (OpenCV imshow overhead)
  - Gesture recognition: 23-26ms every frame (biggest ML bottleneck)
  - Camera limited to 29 FPS by hardware

### 34. Optimized Gesture Recognition Scheduling
- **Changed**: Gestures from every frame → every 2 frames
- **Impact**: Average gesture cost reduced from 25ms → 12.5ms
- **Trade-off**: Still responsive enough for hand tracking
- Kept 2-hand tracking as required for DJ control gestures

### 35. Discovered M1 GPU Delegate Support
- **Major Finding**: MediaPipe supports Metal GPU acceleration on M1!
- **Tested**: `python.BaseOptions.Delegate.GPU` works on Mac Studio
- **Benchmark**: GPU delegate confirmed working with all models
- Created test showing: "✅ GPU delegate supported!"

### 36. Enabled GPU Acceleration for All Models
Added GPU delegate to all MediaPipe models:

- GestureRecognizer: Now GPU-accelerated

## Session 11: Vision Integration Architecture Planning

### 47. Visual Context Integration Strategy for Voice Interaction
**Problem**: How to incorporate continuous vision stream (6 FPS) into conversational AI with 2-3 second response latency

**Research Findings**:
- Scene graphs with 120+ objects exceed LLM context limits (GPT4SGG paper)
- Most systems convert visual to text descriptions, not raw tokens
- No established pattern for temporal visual event buffers in conversational AI
- ROS HRI standards exist but don't address LLM context injection

### 48. Three-Tier Visual Context System Design

**1. Background Scene Context** (Passive, Updates every 30s)
```
[Scene: Workshop setting. Coffee mug on table, laptop open, tools scattered. Evening lighting.]
```
- Lightweight ambient awareness
- Updates only on significant changes
- Doesn't need real-time precision

**2. Active Person Tracking** (Passive, Updates every 5s)
```
[Engaged: Brandon (high confidence)]
```
- Track who's in "interaction zone" (center frame, close to camera)
- More important than general scene
- Quick updates with hysteresis to prevent flip-flopping

**3. Interactive Scanning Tool** (Active, On-demand)
- Tool call: `inspect_visual_target()`
- Lean into robot persona: "Hold it up to my optical scanners..."
- Makes 2-3 second processing delay feel intentional
- Could use vision LLM for detailed analysis

### 49. Person Exit/Re-engagement Handling

**Exit Detection Tiers**:
- **Quick Exit (<3s)**: Continue normally, might be brief step back
- **Medium Exit (3-10s)**: Pause and acknowledge: "I'll wait..."
- **Long Exit (>10s)**: End gracefully: "Catch you later!"

**Re-engagement Logic**:
- <30s away + conversation paused: "Welcome back! As I was saying..."
- <5 min away: "Hey, you're back! What can I help with?"
- >5 min away: Fresh start

**Events**:
- `PERSON_DETECTED` / `PERSON_EXITED`
- `ENGAGEMENT_STARTED` / `ENGAGEMENT_PAUSED` / `ENGAGEMENT_ENDED`

### 50. Implementation Approach

**Phase 1**: Person identification only
- Simple injection: `[Speaking with: Brandon]`
- Add to conversation context at start

**Phase 2**: Scene description
- Background objects/setting awareness
- Update periodically, inject if relevant

**Phase 3**: Interactive scanning
- Tool-based detailed inspection
- "Let me scan that..." narrative cover for latency

### 51. Key Design Insights

**Robot Persona Advantages**:
- Processing delays become "scanning/analyzing"
- Can request specific positioning: "Hold closer to sensors"
- Natural narrative for system limitations

**Context Injection Strategy**:
- Inject minimal context at conversation start only
- Don't update every turn (preserves Claude cache)
- Use events for state changes, not continuous updates

**Selective Relevance**:
- Not all visual events matter for conversation
- Filter by confidence and relevance
- Summarize to 3-5 key facts max

- **MemoryService**: Maintains scene state and engagement tracking

**How Caching Works**:
- First call: System prompt (~2,400 tokens) charged at write rates

- Only new messages are processed fresh

```
Turn 6: System[persona + vision_v2] + Messages[...]
❌ System changed! Cache MISS, rebuild from scratch
```

**Why New Approach Works**:
```
Turn 1: System[persona] + Messages[user + vision_v1] = 2,500 tokens
❌ Below 4,096 minimum - NO CACHE

Turn 5: System[persona] + Messages[...user + vision_v1...] = 4,500 tokens
✅ Cache created! (system + early messages)

Turn 6: System[persona] + Messages[...user + vision_v2]
```
