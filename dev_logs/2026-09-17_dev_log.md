### Problem

From the audit, measured off raw log timestamps in `logs/dj_r3x_2025-11-14_10-44-59.log`:

| Interval | Measured |
|---|---|
| Click-stop → music actually playing | **1,899 ms** |
| Click-stop → R3X starts speaking | **~3,745 ms** |
| Event bus + the entire tool-routing chain | **15 ms** |

The bus was never the problem. 73% of the 1,899 ms was a single Claude round trip whose only
job, for `play_music` / `stop_music` / `set_eye_color`, was to pick a tool name — a decision
that needs no LLM. Worse, tool calls are only extracted after `stream.get_final_message()`, so
**the music could not start until Claude had finished talking.**

### What was built

#### 1. Jev client — `cantina_os/llm/jev_client.py`

Async `httpx` client for the typesafe.ai System One API. Jev answers a fixed set of small
independent questions about one text in a single round trip and returns calibrated
probabilities instead of prose.

- **Model pinned to `jev-1.13.0`**, not `jev-latest`. A silent model bump would move every
  threshold underneath us.
- **One persistent connection, pre-warmed on `engage`.** A cold call measured 437 ms; warm,
  150–290 ms. The TLS handshake is over half the budget, so it is paid at mode change like
  Deepgram's WebSocket, not mid-utterance.
- **`attempts=1`, 800 ms timeout.** No retries on the hot path — a retry costs more than the
  thing it protects. The reference TypeScript client's 6 retries / 120 s default is right for
  batch work and wrong here.
- **Fails open.** `classify()` returns `None` on timeout, HTTP error, or malformed body. It
  never raises into the voice loop.

#### 2. Question design — `cantina_os/llm/jev_intents.py`

Implements "design D" from the benchmark (66 utterances × 5 passes × 8 designs). One request
carries three overlapping reads:

1. a **Choice** over all 6 tools plus `general_chat` / `unclear` — decides *which*;
2. **one Noul per tool** — an absolute "is the speaker asking for *this*, now?";
3. **`is_a_command`** — "instruction, or conversation?".

A tool fires only where all three agree. This was the only benchmark arm with **0 false
triggers and 0 wrong executions in 330 calls**; every choice-only design false-triggers.
The mechanism matters: *"did you turn the music down"* **wins** the Choice competition at 0.94
and **fails** its own Noul at 0.47. The two reads fail independently, and that is what buys the
safety — for one extra request of tokens, not one extra round trip.

**Risk-tiered gates**, because one threshold is the wrong model:

| Tier | Tools | Gate |
|---|---|---|
| Free — instantly reversible | `set_eye_animation`, `next_track` | confidence ≥ 0.75, noul ≥ 0.5 |
| Cheap — reversible but noticeable | `play_music`, `stop_music`, `dj_mode_on/off` | confidence ≥ 0.85 **and** noul ≥ 0.7 |
| Committing — writes shared state | *(empty today)* | never fires from Jev alone |

All configurable via `JEV_CONFIDENCE_THRESHOLD` / `JEV_COMMAND_THRESHOLD`. The free tier is
derived as `threshold - 0.10` so one knob moves both — an early version capped it at 0.75 and
a unit test caught that raising the threshold silently failed to tighten it.

Two deliberate omissions, both from the benchmark:
- **No `volume_up`/`volume_down`.** R3X has no volume tool and they caused the benchmark's
  worst confusions (*"quiet please"* → `volume_down`).
- **No conversation history in `state`.** History raised strict accuracy ~4 points but made the
  router eager and *reintroduced* a false trigger. Only the assistant's identity line goes in —
  that is what fixes *"put on some cantina tunes"* (0.97 with it, `general_chat` without).

#### 3. `JevIntentService` — `cantina_os/services/jev_intent_service.py`

Subscribes to `VOICE_LISTENING_STOPPED` and emits **`INTENT_DETECTED`** — the exact event
`ClaudeService` emits after a tool call. As the audit predicted, this needed **zero changes to
the execution side**: `IntentRouterService` already subscribes and `IntentPayload` already
carries `confidence`.

**Speculative fan-out.** At $0.00006 a call, waiting for the final transcript leaves latency on
the table. `TRANSCRIPTION_FINAL` segments (which fire *during* recording) and debounced
`TRANSCRIPTION_INTERIM` are classified as they arrive and cached by normalized text. When the
authoritative transcript lands and matches, dispatch is **1.6 ms** instead of ~190 ms — the API
latency was paid while the user was still talking. Speculative answers are never acted on
directly; only a matching authoritative transcript can dispatch, so the measured
false-trigger properties are untouched. Cache is cleared per turn, so a stale answer can never
be reused.

#### 4. Dedup — `cantina_os/core/fast_router_gate.py` + `claude_service`

Both services wake on the same event, so without coordination Claude's own `tool_use` would
restart the music a second time and narrate a future it did not cause.

`ClaudeService` now awaits the router's verdict before building its prompt. When an action was
taken it prepends an `<action_already_taken>` XML block (same convention as
`_build_vision_context_for_message`) and sets **`tool_choice={"type": "none"}`** — tools stay in
the request so the prompt cache still hits, but Claude can only speak. `INTENT_CONSUMED` is
also emitted for anything that wants to observe the decision.

This costs the *spoken* path ~190 ms and the *action* path nothing — the music is already
playing before Claude is called. Fail-open by construction: no router registered → no wait at
all; router hung → bounded 1.2 s timeout, then the turn proceeds exactly as it does today.

#### 5. New voice-reachable intents

`IntentRouterService` gained `next_track`, `dj_mode_on`, `dj_mode_off` (→ `dj next` / `dj start`
/ `dj stop` CLI commands, which existed all along) and `set_eye_animation` as an alias of
`set_eye_color`. **DJ mode is now reachable by voice for the first time** — Claude has no tool
schema for it, so previously only the CLI or dashboard could start it.

### Blocking-event-loop fix

The audit's central finding: the **synchronous** `Anthropic` client called from 7 sites inside
`async def`. Proof in the logs — a **1,817 ms window in which not one of 22 services wrote a
line**, then all 13 "streamed" chunks arriving in a **2 ms burst**. That is the "mouth freeze"
two previous commits chased without finding the cause; the eyes, mouth LEDs and music ducking
all stalled with it.

Fixed with `asyncio.to_thread` (the pattern already in `vision_service.py:344`) at the four
live sites: main streaming turn, non-streaming turn, verbal feedback, DJ commentary, plus the
warmup. For the streaming path the whole blocking read moves to a worker thread and each chunk
is marshalled back with `run_coroutine_threadsafe`, so **streaming is now real downstream, not
just on the wire.** The two inert interim-draft sites were left alone.

Verified by a heartbeat coroutine: the event loop ticked **175 times** during a turn that
included both the Jev call and a blocking Claude call.

### Dead event topics

Two casualties of topic-name drift, both one-line fixes:

- **`MemoryService`** (`memory_service.py:305`) subscribed to `LLM_RESPONSE_TEXT`, which nothing
  emits. It recorded what Brandon said and **never what R3X replied**, so every person summary
  was built from a one-sided transcript. `LLM_RESPONSE_TEXT` → `LLM_RESPONSE`. This is very

- **`LatencyTrackerService`** subscribed to `LLM_RESPONSE_TEXT` and
  `SPEECH_SYNTHESIS_STARTED`/`_ENDED`, none of which are emitted. Corrected to `LLM_RESPONSE`,

⚠️ **The latency tracker still will not record.** Beyond the topic names there is a second,
unrelated defect: every handler keys on `conversation_id`, but `VOICE_LISTENING_STARTED` carries

different value. The ids never match, so metrics are still dropped. Unifying them is a real
change, not a one-liner, and was left out of scope. All latency numbers below come from

### Install-guard fix — and the trap underneath it

`start-dashboard.sh:191-198` read `if [ ! -f .requirements_installed ]`. The first run ever
created that sentinel, and **every dependency change since Nov 7 2025 was silently skipped** —
which is why the venv sat on `anthropic` 0.52.2 while `requirements.txt` asked for ≥0.72.0.
Confirmed on disk: an empty sentinel dated Nov 7 2025. Now keyed on a SHA-256 of
`requirements.txt`, and a failed install is not stamped so the next run retries.

**Fixing the guard alone would have broken DJ R3X on the next start.** With the guard working,
unbounded `anthropic>=0.72.0` resolves to **1.6.0**, and anthropic 1.x **removes `temperature`
from `messages.create()` with no `**kwargs` passthrough**. Every Claude call in
`claude_service`, `vision_service` and `memory_service` would have raised `TypeError`. Verified
directly against both SDKs in throwaway venvs.

So `requirements.txt` now pins `anthropic>=0.72.0,<1.0`, which resolves to 0.125.0 — keeps
`temperature`, and has `ToolChoiceNoneParam`. Migrating to 1.x is separate, deliberate work.

⚠️ The next `./start-dashboard.sh` will install `requirements.txt` **for the first time since
November 2025**. `deepgram-sdk`, `openai`, `elevenlabs` and the rest will move too. Worth
watching that first start.

### Measured results

**transcript → `MUSIC_COMMAND` on the real event bus**, real Jev API, real
`IntentRouterService` + `CommandDispatcherService`, hardware mocked:

| Path | Measured | vs baseline |
|---|---|---|
| Audit baseline (Claude tool call) | **1,899 ms** | — |
| Jev router, warm, 5 consecutive turns | **p50 197 ms** (min 160, max 260) | **9.6× faster** |
| Jev router, speculative cache hit | **1.6 ms** | **~1,190× faster** |
| — of which Jev network round trip | 158–257 ms | |
| — of which all of CantinaOS | **2–3 ms** | confirms the audit's 15 ms finding |

Other measured intervals: `DJ_COMMAND` 199 ms, `EYE_COMMAND` 225 ms, `stop music` 271 ms.
Action leads the spoken reply by ~209 ms, and the ordering assertion (action strictly before
reply) holds.

**Classifier accuracy, real API, 30 utterances including noisy STT variants:**

```
exact match                        29/30 (96.7%)
FALSE TRIGGERS on conversation      0
wrong tool fired                    0
declined a real command             1   -- "quiet please"
latency  p50=188 ms  p95=279 ms  min=150  max=287
cost     1409 input tokens, $0.0000592 per call  (~17,000 utterances per dollar)
```

The single miss is the *safe* failure: "quiet please" is declined and falls through to Claude,
which handles it as it always has. That asymmetry is the whole design — a miss costs one slow
turn, a false trigger blasts music into the room while someone was asking a question.

**Honest note on the ~100 ms target:** it is not reachable on the non-speculative path. The Jev
round trip alone is p50 ~188 ms, of which ~86 ms is raw network RTT. CantinaOS contributes 2–3 ms
— there is nothing left to optimize on our side. The speculative path *does* beat it (1.6 ms)
whenever a partial transcript matches, which is the common case for short commands.

#### The `.gitignore` discovery

`.gitignore:52` had an unanchored `test_*.py`. It ignored **the entire real test suite**.
Every existing test file had been force-added at some point, and any newly written test was
invisible to `git status` and silently left out of commits. Anchored it to the throwaway
scratch scripts that actually live at the repo root, and that one change picked up **14 test
files that had been written and never tracked**.

#### The trap that had been eating tests silently

`main.py:162` builds a `pyee.AsyncIOEventEmitter`, whose `emit()` is **synchronous** — it
returns `bool` and schedules coroutine handlers on the loop. `BaseService.emit()`/
`subscribe()` therefore call it without `await`, which is correct.

Several test files and both shared mocks defined `emit`/`on` as `async def`. An unawaited
coroutine never runs its body, so those tests **observed nothing and passed for the wrong
reason** — or timed out waiting for an event that was never delivered. This accounted for
dozens of failures across four files. It is now documented in CLAUDE.md as trap #1, because
it will happen again otherwise.

Related, and still live in production: `cantina_os/event_bus.py`'s `EventBus` class declares
`emit`/`on` as `async def`. Nothing in the current wiring uses it, but it is imported for
typing in several services and is a landmine for anything that instantiates it.

#### deepgram-sdk stays on 5.x, and this one is not a judgement call

6.x and 7.x **delete the `deepgram.extensions` package outright**. The live STT service needs
`deepgram.extensions.types.sockets.ListenV1ControlMessage`
(`deepgram_direct_mic_service.py:22`, used at `:326`). Verified by import against both 6.1.1
and 7.9.0 — both fail. The 7.x equivalent is `deepgram.listen.v1.ListenV1KeepAlive`, which
means rewriting the only live STT path with no microphone and no Deepgram budget to validate
it against. Took the highest 5.x instead and wrote the reason into the requirements file.

So the audit's "5→7 is a test-and-bump, not a rewrite" was **wrong**, and only running the
install revealed it.

New harness: `cantina_os/scripts/system_smoke_run.py`. It boots a real `CantinaOS` and

**Real**: the event bus, `JevIntentService` against the live typesafe.ai API,

**Mocked**: the Arduino / eye LEDs.
**Skipped**: mic capture, the mouse trigger, vision — all three need hardware and OS

#### Two real bugs the system run found, both invisible to unit tests

**1. Eye colour requests were dispatched and then thrown away. FIXED.**

"make your eyes red" was classified correctly and dispatched in 209 ms — and then died at a
CLI arg check. Two independent defects, both pre-existing; the Jev branch only inherited them
by adding `set_eye_animation` as an alias:

- The router emitted `CLI_COMMAND` as `eye pattern <pattern> <color>` — **two args**. The
  compound command "eye pattern" is registered with `max_args=1` (`main.py:349`), so
  `command_decorators.py:368` rejected every colour request with *"Command 'eye pattern'
  accepts at most 1 arguments, got 2"*. Even with the count fixed,
  `EyeCliCommandPayload.from_cli_payload` parses only `pattern_name` — **the CLI grammar has
  no colour slot at all.**
- The default pattern was `"solid"`, which is **not a member of `EyePattern`**. Any colour
  request without an explicit pattern was rejected by the eye service too.

Fixed by emitting `EYE_COMMAND` directly — `_handle_eye_command` already accepts a dict of
pattern/color/intensity/duration and passes all four to `set_pattern()`, which does take a
colour — and defaulting to `custom`, the member documented as being "For custom patterns with
specific colors". `tests/test_eye_intent_routing.py`, 6 tests on the real bus.

**2. `next_track` does nothing outside DJ mode. DOCUMENTED, not papered over.**

`dj next` is the system's only skip capability, and `BrainService` refuses it with *"Cannot
skip track, DJ mode is not active"*. `MusicControllerService` understands only `"play"` and
`"stop"` (`music_controller_service.py:574,577`), so there is no playlist cursor to advance.
Deliberately **not** faked by re-issuing `music play` — that picks a track the same way a
fresh "play some music" does, which is not what "next" means and would hide the gap. The fix
belongs in `MusicControllerService`. The user does at least get an accurate error today.

The lesson worth keeping: both bugs **classified correctly, dispatched correctly, and were
discarded downstream.** Every unit test in the repo would have passed. Only running the thing
found them.

### Latency tracker: conversation_id unified

Session 1 left this as "a real change, not a one-liner, out of scope". Done now, and it was
two breaks on the same id:

1. The capture services minted a turn id, put it on `VOICE_LISTENING_STARTED`, then **threw
   it away** — `deepgram_direct_mic_service.py:528` emitted `{"transcript": ...}` and
   `cli_service.py:376` (the typed `done` path) emitted a bare `{}`, even though `record` had
   minted an id two dozen lines earlier.
2. `ClaudeService` stamped `LLM_RESPONSE` with its **own** `_current_conversation_id`, minted
   independently in `reset_conversation()`.

Fixed by making the capture service the single owner — it is the only component that knows
when a turn began, which is what the whole measurement is relative to. Both emitters carry
it; `_handle_voice_transcript` adopts the incoming id. An absent id leaves the existing one
alone, so nothing regresses.

**Second thing this fixed, found while tracing it**: `CLIService._handle_llm_response`
(`cli_service.py:600`) has the same guard. Because the ids never matched, **the CLI was
silently discarding R3X's replies** instead of printing them. That had never been reported as
a latency bug.

`tests/test_latency_conversation_id.py`, 6 tests — including one that characterises the *old*
mismatched behaviour, so a regression is visible rather than silent. The tracker now logs
"1 active conversations, 1 completed" where it previously recorded nothing.

Still partial: the tracker also subscribes to `TRANSCRIPTION_FINAL`, so the transcription leg
depends on what `deepgram_direct_mic_service.py:451` sends.
